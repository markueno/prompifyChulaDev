Executive Summary
What we are building, why, and what it costs
THE PROBLEM

Prompify users face four persistence gaps today:

  1. Blank IDE on refresh — generated projects replay 90+ seconds of shell history every time the page loads
  2. No codebase history — users cannot roll back to a previous version of their generated app
  3. Runtime data loss — CRM contacts, HR records, and other business data inside generated apps have no guaranteed persistence
  4. No offline resilience — if the server is unreachable, the app stops working entirely
THE SOLUTION

Three components added to our existing stack:

  1. Codebase Snapshots — instant project restore from browser cache + Cloudflare R2, no shell replay
  2. Data Proxy — Remix server mediates all generated-app database access with real tenant isolation
  3. Offline Queue + Circuit Breaker — edits save locally when offline, sync when reconnected

WHAT WE ARE NOT DOING
  • Not building on Redis — Redis is in our docker-compose file but the app has zero Redis imports. Our sessions already live in PostgreSQL. No need to add Redis infrastructure.
  • Not storing giant JSONB blobs in PostgreSQL — at 10,000 users this would be 300GB+ in one table, creating backup and autovacuum nightmares. We use object storage from day one.
  • Not exposing PostgREST to end users for multi-tenant data — the Accept-Profile header is attacker-controlled; this would be a cross-tenant data exposure vulnerability. We mediate all access through our Remix server.

CRITICAL GAP FOR 10,000+ USERS

The production app runs as a single Vite dev server process (pnpm run dev) with a connection pool of 20. There is no production build, no PgBouncer, no read replica, no load balancing, and no backup strategy beyond the Docker volume. This cannot survive production traffic at any meaningful scale.

The Four Persistence Problems We Must Solve
Every architectural decision maps to exactly one of these problems
PROBLEM 1: Chat History

Already solved. User prompts + AI responses (including embedded file content as XML) are persisted via IndexedDB + PostgreSQL dual-write. Messages survive refresh, survive server restart, and sync across devices when the user logs in.

No changes needed for this problem.

PROBLEM 2: Codebase Snapshots

Not solved. When a user refreshes the page, the WebContainer is destroyed. The IDE must replay every shell command from the chat history to rebuild the project — 90+ seconds of npm install + npm run dev. Files edited manually outside of AI generation are lost.

Solution: Content-addressed snapshots in R2 + IndexedDB cache.

PROBLEM 3: Runtime App Data

Partially solved via Supabase. Generated apps (CRM, HR tools) store business data in per-app PostgreSQL schemas. But this depends on Supabase as an external vendor. At 10,000 users, Supabase costs ~$5,000-10,000/month.

Solution: Self-hosted data proxy in Remix, schemas in our own PostgreSQL.

PROBLEM 4: Version Control

Not solved. No way to view or restore previous project states. Users cannot undo mistakes, compare versions, or branch their work. Every save overwrites the previous state invisibly.

Solution: Append-only version history with rollback-as-new-version pattern.

Codebase Snapshots: The Core Innovation
How we solve "blank IDE on refresh" permanently

The User Experience Today

  1. User generates a React app via AI — 30 files, npm install, dev server running
  2. User edits src/App.tsx manually in the IDE
  3. User refreshes the page
  4. WebContainer is destroyed. All files in memory are gone.
  5. The system replays every <boltAction> from the chat history — re-executing npm create vite, npm install (90 seconds), every file write, every shell command
  6. User's manual edit to App.tsx is lost — only AI-generated files are restored
  7. Total time until IDE is usable: 90-120 seconds

The User Experience After Snapshots

  1. User generates a React app via AI — 30 files, npm install, dev server running
  2. Every AI generation and every manual file save automatically creates a snapshot
  3. User refreshes the page
  4. Snapshot loads from IndexedDB in <100ms. All 30 files are written to WebContainer.
  5. Only npm install && npm run dev runs — no shell history replay
  6. User's manual edit is preserved in the snapshot
  7. Total time until IDE is usable: 15-25 seconds (just dependency install)

Storage: Each file is stored once by its SHA-256 hash. When a user changes one line in one file, only that new file version is uploaded to Cloudflare R2. All unchanged files from previous versions are referenced by their existing hashes — zero additional storage cost. This is how Git works internally (git-scm.com/book/en/v2/Git-Internals-Git-Objects).

Why Content-Addressed Storage (Not JSONB in PostgreSQL)
The single most consequential architectural decision in this proposal

The Original Proposal's Approach (Rejected)

-- Each snapshot stores the ENTIRE project as one JSONB blob
INSERT INTO codebase_snapshots (snapshot) VALUES (
  '{"files": {"src/App.tsx": "import React...", "src/index.tsx": "import...", ...}}'
);

The arithmetic at 10,000 users:
10,000 users × ~5 chats × 30 retained versions = 1.5 million rows
Even at 200KB compressed per snapshot (TOAST LZ compression): 300GB in one table.
Every save rewrites the ENTIRE project as one new row + full WAL entry.
pg_dump on 300GB takes 30-60 minutes. PITR replay is even slower.

Source: postgresql.org/docs/current/storage-toast.html — TOAST chunks values >2KB into separate physical rows. Large JSONB values are compressed but still stored row-by-row with full WAL logging.

Our Approach: Content-Addressed File Storage

-- The version stores ONLY a manifest (tiny JSONB, ~3KB for 100 files)
INSERT INTO codebase_versions (manifest) VALUES (
  '{"src/App.tsx": "sha256:abc123...", "src/index.tsx": "sha256:def456..."}'
);

-- Each unique file content is stored exactly once in R2
-- Blob path: blobs/ab/c3/abc123... (content-addressed in R2 bucket)
-- PostgreSQL tracks references: codebase_blobs table with ref_count

Why this is dramatically cheaper:

  • A package.json, vite.config.ts, or index.html generated by the AI is identical across thousands of projects. Content-addressing stores each unique file once — the same blob is referenced by 50,000 manifests. This is automatic, zero-config deduplication.
  • A user changing one line in App.tsx uploads only that one new blob. Every other file is already stored. Compare this to JSONB: the ENTIRE project gets re-serialized and re-TOASTed.
  • PostgreSQL stores only small manifest JSONB (~3KB per version → ~4.5GB total at 1.5M versions — trivial).
  • R2 costs: $0.015/GB-month storage, $0.36/million reads, $0.00 egress. At 10,000 users with heavy deduplication, estimated 100GB stored = $1.50/month.

Source: developers.cloudflare.com/r2/pricing/ — "Egressing directly from R2 does not incur data transfer (egress) charges and is free."

WHY THE FOR UPDATE LOCK MATTERS

Without SELECT ... FOR UPDATE on the chat row, two concurrent saves from different tabs could both execute the UPDATE (unmarking latest) and then both try to INSERT with is_latest = true. The partial unique index WHERE is_latest = true would reject the second one — silently dropping a save. The row-level lock makes this atomic: the second transaction waits until the first commits, then sees the updated state.

Source: postgresql.org/docs/current/explicit-locking.html — "FOR UPDATE causes the rows retrieved by the SELECT to be locked as though for update. This prevents them from being locked, modified or deleted by other transactions."

Version Control: Append-Only History with Rollback
Users can view, compare, and restore any previous project state

Database Schema

CREATE TABLE IF NOT EXISTS codebase_versions (
    id SERIAL PRIMARY KEY,
    chat_id TEXT NOT NULL REFERENCES chats(id) ON DELETE CASCADE,
    user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    version_number INTEGER NOT NULL,
    is_latest BOOLEAN NOT NULL DEFAULT false,
    manifest JSONB NOT NULL,  -- { "src/App.tsx": "sha256:abc...", ... }
    description TEXT,
    file_count INTEGER NOT NULL DEFAULT 0,
    total_bytes INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    UNIQUE(chat_id, version_number)
);

CREATE UNIQUE INDEX idx_versions_latest_per_chat
ON codebase_versions(chat_id) WHERE is_latest = true;

Rollback Creates a New Version (Never Mutates History)

-- POST /api/chats/{chatId}/rollback?version=3
BEGIN;
  SELECT 1 FROM chats WHERE id = $1 FOR UPDATE;  -- lock

  UPDATE codebase_versions SET is_latest = false
  WHERE chat_id = $1 AND is_latest = true;

  INSERT INTO codebase_versions
    (chat_id, user_id, version_number, is_latest, manifest,
     description, file_count, total_bytes)
  SELECT chat_id, $2,
    (SELECT COALESCE(MAX(version_number), 0) + 1
     FROM codebase_versions WHERE chat_id = $1),
    true, manifest,
    'Rollback to v' || version_number,
    file_count, total_bytes
  FROM codebase_versions
  WHERE chat_id = $1 AND version_number = $2;

  -- Bump ref_count on all blobs in the restored manifest
  UPDATE codebase_blobs SET ref_count = ref_count + 1
  WHERE sha256 IN (
    SELECT value FROM jsonb_each_text(
      (SELECT manifest FROM codebase_versions
       WHERE chat_id = $1 AND version_number = $2)
    )
  );
COMMIT;

This is the same pattern used by MediaWiki (Wikipedia's engine): "Reverts create new revisions pointing to the old content, never modifying history." (mediawiki.org/wiki/Manual:Revision_table). It is also how Git's object model works — every commit references a tree of content hashes.

A user can roll back from v7 to v3, then later roll back from v8 to v7. Every state is preserved. No data is ever deleted from the history.

Runtime App Data: Why We Cannot Use PostgREST Directly
A verified security analysis of the original proposal's approach

The Original Proposal's Approach (Rejected on Security Grounds)

Design: One PostgREST instance. One shared app_user database role. Thousands of app_{chatId} schemas. Client selects schema via Accept-Profile: app_abc123 HTTP header.

Security claim in original: "Even if a user crafts a request with a different schema in the header, they'll get a permission denied because app_user only has GRANT on schemas owned by that user."

This claim is false. Here is why:

Verified: How PostgREST Schema Routing Actually Works

  1. PostgREST only serves schemas listed in PGRST_DB_SCHEMAS. A request with Accept-Profile: some_schema is REJECTED with HTTP 406 (error PGRST106) if that schema is not in the configured list. Source: docs.postgrest.org/en/stable/references/api/schemas.html
  2. To serve thousands of schemas, you must list them all in PGRST_DB_SCHEMAS. This requires the pre_config() function + NOTIFY pgrst, 'reload config' + NOTIFY pgrst, 'reload schema' on every new app creation. Source: docs.postgrest.org/en/stable/configuration.html — "In-Database Configuration"
  3. Each schema reload re-introspects EVERY exposed schema, table, column, FK, and function. The docs state: "Requests will wait until the schema cache reload is done." At 10,000 schemas × N tables each (potentially 50,000+ relations), this becomes a multi-second blocking operation. Source: docs.postgrest.org/en/stable/references/schema_cache.html
  4. PostgreSQL GRANT operates at the ROLE level, not the user-instance level. There is exactly one shared app_user role. If that role has USAGE on 10,000 schemas, then ANY user whose JWT resolves to app_user can access ANY schema. The Accept-Profile header is the ONLY thing separating tenants — and it is attacker-controlled. Source: postgresql.org/docs/current/ddl-priv.html — "Privileges are granted to roles."
THE ORIGINAL RLS POLICY IS A NO-OP
CREATE POLICY tenant_isolation ON app_{chatId}.contacts
    USING (true)    -- ← This evaluates to true for EVERY row, ALWAYS
    WITH CHECK (true);

USING (true) means "this policy evaluates to true for every row." It is a literal no-op that provides zero row-level isolation. Source: postgresql.org/docs/current/ddl-rowsecurity.html — "Rows for which the expression does not return true will not be processed. [...] CREATE POLICY all_view ON passwd FOR SELECT USING (true); — Normal users can view ALL rows."

Runtime App Data: The Corrected Data Proxy Architecture
Mediating all generated-app database access through our Remix server

The Data Proxy Pattern

The generated app's frontend never talks to PostgreSQL or PostgREST directly. It calls our Remix server, which:

  1. Validates the session JWT (same auth system already in auth.ts)
  2. Verifies the user owns the chat (chatId → userId mapping in the chats table)
  3. Derives the schema name server-side (the client never sends a schema selector)
  4. Sets transaction-scoped variables for RLS awareness
  5. Executes the query as a single low-privilege database role
// app/routes/api.data.$chatId.$resource.ts — NEW Remix route

export const loader = async ({ request, params, context }) => {
  // 1. Validate session JWT (existing auth)
  const user = await requireAuth(request, context);

  // 2. Verify ownership — server-side, NEVER trust the client
  const chat = await getChatById(params.chatId);
  if (!chat || chat.userId !== user.id) return json({ error: 'Not found' }, 404);

  // 3. Derive schema — client CANNOT control this
  const schema = schemaForChat(params.chatId);  // "app_abc123"

  // 4. SQL injection prevention — whitelist resource names
  if (!/^[a-zA-Z_][a-zA-Z0-9_]*$/.test(params.resource)) {
    return json({ error: 'Invalid resource' }, 400);
  }

  // 5. Execute with transaction-scoped settings
  const pool = getPostgresReadPool();
  await pool.query('SET LOCAL statement_timeout = \'5s\'');
  await pool.query('SET LOCAL app.current_user_id = $1', [user.id]);
  await pool.query('SET LOCAL search_path TO ' + schema);

  const result = await pool.query(
    `SELECT * FROM ${params.resource} LIMIT 1000`
  );

  return json({ data: result.rows });
};

Real RLS (Not a No-Op)

Every generated app table gets a tenant_user_id column and a policy that actually does something:

ALTER TABLE app_{chatId}.contacts ADD COLUMN tenant_user_id TEXT
    DEFAULT current_setting('app.current_user_id');

ALTER TABLE app_{chatId}.contacts ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON app_{chatId}.contacts
    USING (tenant_user_id = current_setting('app.current_user_id'))
    WITH CHECK (tenant_user_id = current_setting('app.current_user_id'));
WHY THIS IS SECURE
  • The client CANNOT choose the schema — it's derived server-side from the validated JWT + chat ownership check
  • The data proxy role (prompify_data_proxy) is never exposed to end users — only the Remix server has its credentials
  • RLS provides defense-in-depth: even if a query somehow escapes the server-side check, the policy blocks rows belonging to other users
  • Statement timeout (5s) prevents one generated app from DoS-ing the database
  • Row limit (1000) prevents accidental large result sets
Offline Resilience: The Browser Is the Primary Runtime
Users can continue working when the server is unreachable. Edits sync when reconnected.

Design Principle

The browser IDE (WebContainer) is the authoritative runtime. The server provides durability and cross-device sync. When the server is unreachable, the app degrades gracefully rather than failing.

Components

1. PENDING WRITES QUEUE (IndexedDB)

When a snapshot save fails because the server is unreachable:

  • The snapshot is saved to IndexedDB pendingWrites store
  • Entry: { type: 'snapshot', chatId, manifest, timestamp, retryCount }
  • UI shows amber banner: "Saved locally — syncing when reconnected"
  • Chat messages are also queued (they already work offline via IndexedDB)

This is the Transactional Outbox Pattern documented by Microsoft's Cloud Design Patterns — the same pattern used by Google Docs, Figma, and Linear for offline-first operation.

2. CIRCUIT BREAKER (localStorage)

Prevents hammering an unreachable server:

  • State: closed → open → half-open (standard circuit breaker)
  • After 3 consecutive failures, circuit opens (30-second cooldown)
  • UI shows "Working offline" indicator when circuit is open
  • Persisted to localStorage — survives page refresh (unlike the original proposal which stored state in memory)
3. QUEUE DRAIN ON RECONNECT

Triggered by:

  • navigator.onLine event
  • Successful health check after circuit half-opens
  • Page load (in case tab was closed while offline)

Drains pending writes in timestamp order. On success: delete from queue. On failure: increment retry count, stop draining.

4. UI STATE COMMUNICATION

Circuit closed: Normal operation, no indicator

Circuit open: Amber banner — "Working offline — edits save locally"

Circuit half-open: "Reconnecting..." spinner

Queue draining: "Syncing 3 pending changes..." progress

Chat input disabled when offline (AI generation requires server)

IDE editing, preview, terminal all continue working (browser-only)

Failure Scenario Walkthrough

  1. User is editing a generated React app. Server goes down.
  2. User saves a file. Snapshot is written to IndexedDB + queued as pending write. "Saved locally" banner appears.
  3. User makes 5 more edits. All saved to IndexedDB. Queue now has 5 pending snapshots.
  4. User refreshes page. Circuit breaker state is loaded from localStorage — circuit is still open. Snapshot is loaded from IndexedDB cache. IDE works.
  5. Server comes back. Health check succeeds. Circuit goes to half-open → drain begins.
  6. All 5 pending snapshots are uploaded in order. On success, each is removed from queue. "Syncing" banner disappears.
  7. On next save, circuit is fully closed. Normal operation resumes.
Production Infrastructure for 10,000+ Users
What must change from the current docker-compose setup before scaling

Current Production Setup (Non-Viable at Scale)

  • Single Vite dev server — pnpm run dev in docker-compose.prod.yaml:129
  • Connection pool size 20 — max: 20 in database-postgresql.ts:21

Runtime App Data — app_{chatId} schemas (PostgreSQL, same instance)

Each generated app (CRM, HR tool, inventory system, etc.) gets its own PostgreSQL schema:

  • Schema name: app_{chatId} (with hyphens replaced by underscores) — matches existing schemaForChat() in supabase-provision.server.ts:48-50
  • Access: Through Remix data proxy only. Never exposed to PostgREST for multi-tenant endpoints.
  • Grants: GRANT USAGE, SELECT, INSERT, UPDATE, DELETE TO prompify_data_proxy — a single low-privilege role that only the Remix server uses
  • RLS: Every table gets tenant_user_id column + USING (tenant_user_id = current_setting('app.current_user_id'))
NOTE ON SCHEMA COUNTS

At 10,000 users, we expect ~50,000 app schemas. PostgreSQL has no hard limit on schemas (postgresql.org/docs/current/limits.html lists limits for databases, relations, rows — schemas are not directly bounded). However, practical concerns (pg_dump time, catalog bloat, autovacuum pressure) are real. We mitigate by: (1) keeping schemas physically small (the Remix proxy ensures this), (2) using a separate PostgreSQL instance for runtime data if catalog pressure becomes an issue, and (3) monitoring pg_stat_user_tables for bloat. The schema-per-app pattern is a well-documented multitenancy strategy (docs.citusdata.com/en/stable/develop/migration_mt_schema.html).

Security Model: Defense in Depth
How tenant isolation, authentication, and data protection are enforced at every layer

Authentication Layers

LayerMechanismEnforcement Point
Session Auth JWT signed with JWT_SECRET. 24h expiry. Validated against user_sessions table (SHA-256 hash match). auth.ts:82-107 — every Remix loader/action
Data API Auth Separate secret (DATA_API_SECRET). Short-lived token (15 min). Scoped to specific chatId. Generated apps exchange session JWT for data token. api.data.$chatId.$resource.ts — new Remix route
PostgreSQL Auth Two roles: prompify_app (full access to public schema, server-side only) and prompify_data_proxy (per-schema grants, server-side only). Neither role is exposed to end users. PostgreSQL pg_hba.conf
CRITICAL: NEVER REUSE JWT_SECRET FOR DATA API TOKENS

The session JWT (JWT_SECRET) and data API tokens (DATA_API_SECRET) MUST use different secrets. If the same secret is used for both, a compromise of the session JWT (issued client-side, visible in browser storage) would also compromise data API access to all generated apps. Source: OWASP Authentication Cheat Sheet — "Separate authentication contexts should use separate keys."

Tenant Isolation Layers (Strongest → Weakest)

  1. Server-side ownership check: Remix loader validates chat.userId === session.userId before allowing any data access. The client never sends a schema selector.
  2. Schema namespace isolation: Each app's tables live in app_{chatId} schema. The search_path is set server-side per request.
  3. Row-Level Security: Every app table has a real RLS policy that checks tenant_user_id = current_setting('app.current_user_id'). This is belt-and-suspenders AFTER the server-side check.
  4. Statement timeout: SET LOCAL statement_timeout = '5s' prevents any single query from blocking the database.

Snapshot Security

  • R2 bucket is private — never publicly accessible
  • All blob access goes through Remix server, which validates auth + ownership
  • Presigned URLs for upload/download are 60-second TTL, single-use
  • Consider SSE-S3 encryption at rest for the R2 bucket (nil additional cost)
  • Snapshots are secret-bearing: generated source code routinely contains API keys, connection strings, and secrets the model wrote into files. Treat the snapshot store as you would a secrets manager.

Supabase Migration Strategy
How we move from external Supabase to fully self-hosted without downtime

Current State

The codebase already has a well-abstracted Supabase integration:

  • supabase-provision.server.ts — provisions schemas, fetches table metadata, runs admin queries via Supabase Management API
  • api.deploy.ts:114-137 — injects env-config.js with supabaseUrl, supabaseAnonKey, supabaseSchema
  • LLM prompt templates instruct generated code to use @supabase/supabase-js with window.__PROMPIFY_CONFIG

Migration Path (No Urgency — Phased, Reversible)

StageWhat ChangesDuration
Stage 1: Dual-Write (Now) New generated apps use the Remix data proxy and our own PostgreSQL schemas. Existing apps continue using Supabase. Both paths coexist. The env-config.js injection switches based on a feature flag. Built into Phase 4
Stage 2: Migration Tooling (Week 6-8) Build a schema/data export tool that copies an app's Supabase schema + data into our PostgreSQL. The LLM prompt template is updated to generate fetch()-based database code (not Supabase SDK). 1-2 weeks
Stage 3: Phased Migration (Week 8-16) User-by-user migration. When a user explicitly chooses to migrate (or when their Supabase quota is exceeded), the tool copies their data. The generated app is redeployed with the new env-config.js pointing at our data proxy. Ongoing
Stage 4: Supabase Deprecation (When Ready) All remaining apps are migrated. Supabase integration code is removed. env-config.js always points at our data proxy. Supabase subscription is cancelled. 1 week
WHY THERE IS NO URGENCY TO MIGRATE
  • Supabase is working fine for the apps currently on it. Migration is a cost optimization, not a reliability fix.
  • The data proxy architecture works whether the backend is our PostgreSQL or Supabase — it's an abstraction layer.
  • Our PostgreSQL + data proxy is incrementally cheaper per-user. As we scale, the cost savings compound.
  • The dual-write stage ensures zero downtime. Users are never forced to migrate.
Executive FAQ: Anticipated Questions
Answers prepared for leadership, security, and operations stakeholders
Q: "Why not just use Supabase? It's already integrated."
Supabase works at 100 users (~$75-200/mo) but at 10,000 users with per-app schemas, Supabase costs $5,000-10,000/month. Our self-hosted equivalent costs ~$200/month — a 25-50× cost reduction. More importantly, Supabase means our customers' runtime app data lives on a third-party service we don't control. If Supabase has an outage, every generated app is down. By self-hosting, we own the availability story end-to-end. Migration is phased and reversible — we dual-write before cutting over.
Q: "Is this architecture proven? Has anyone done this before?"
Yes. Every component is a proven open-source technology: PostgreSQL (40 years, used by every major tech company), PgBouncer (standard connection pooler, used by Instagram, Heroku), Cloudflare R2 (S3-compatible, used by thousands of production workloads), Remix (used by Shopify). The schema-per-tenant pattern is documented by Microsoft/Citus (docs.citusdata.com). The content-addressed storage pattern is how Git works internally. The outbox/circuit-breaker patterns are published by Microsoft's Cloud Design Patterns team. This is not novel — it's composed of well-understood building blocks.
Q: "What happens if the database goes down?"
The browser is the primary runtime. Chat messages, codebase snapshots, and pending writes all live in the browser's IndexedDB. Users can continue editing their generated apps. The IDE works fully offline. When the database recovers, pending writes are synced. Cross-device access and AI generation (which requires the server) are unavailable during the outage.
Q: "How do we prevent one user's heavy app from slowing down everyone else?"
Three layers: (1) Statement timeout of 5 seconds on every data proxy query — no single query can run longer than that. (2) Row limits (1000 rows max) prevent accidental large result sets. (3) Rate limiting per chatId (100 requests/minute) in the Remix loader. For extreme cases, we can shard app schemas across multiple PostgreSQL instances by hashing the chatId — this is a configuration change, not a code rewrite.
Q: "What about GDPR / data residency? Can we store data in specific regions?"
Cloudflare R2 supports region selection for buckets. PostgreSQL can be deployed in any region your VPS provider supports. Since we self-host everything, we have full control over where data physically resides. This is a significant advantage over Supabase, where data residency options are limited to their supported regions.
Q: "How do we know if the architecture is working correctly at scale?"
Phase 3 includes monitoring: pg_stat_statements for query performance, disk usage alerts at 70%, connection pool wait time metrics, replication lag monitoring, and R2 operation metrics. We also run a monthly restore drill (restore from PITR backup to a test instance) to verify backup integrity. The circuit breaker state is visible in the browser — if users start seeing "Working offline" indicators, we know there's a server issue before they report it.
Q: "Can a user's snapshot contain secrets that shouldn't be stored?"
Yes. Generated source code routinely contains API keys, database connection strings, and other secrets the AI model writes into files — this is true regardless of whether we store snapshots. Our approach: the R2 bucket is private, all access is mediated through the Remix server (which validates auth + ownership), presigned URLs are short-lived (60 seconds), and we recommend SSE-S3 encryption at rest. The snapshot store should be treated with the same security posture as a secrets manager.
Q: "What's the rollback plan if this architecture doesn't work?"
Every phase is independently shippable and reversible. Phase 1 (snapshots) can be disabled with a feature flag — the system falls back to message replay (current behavior). Phase 4 (data proxy) dual-writes with Supabase — we can switch back by changing the env-config.js injection. Phase 3 (production build) can be rolled back by reverting the docker-compose file. There is no "big bang" cutover. Each phase de-risks the next.
Q: "Why not use Redis? Our docker-compose already has it."
Redis is configured in docker-compose but the app code (verified by grepping all TypeScript files) has zero imports of ioredis or redis. It was likely planned but never wired up. Our sessions already live in PostgreSQL's user_sessions table. Adding Redis would mean: (1) an additional stateful service to monitor and back up, (2) a new failure mode (what if Redis is down but Postgres is up?), and (3) additional operational complexity. PostgreSQL handles sessions + scheduled tasks + queue state without Redis — and it's already our source of truth.
Q: "How many engineers do we need to maintain this?"
Post-build: 1 backend engineer for ongoing maintenance. PostgreSQL and PgBouncer are mature, stable technologies that require minimal upkeep (mostly version upgrades and disk monitoring). R2 is a managed service — no maintenance required. The Remix data proxy is ~200 lines of code. The snapshot system is the most complex component (~500 lines of server code + ~300 lines of client code). Total code footprint for the entire architecture: approximately 1,500-2,000 lines of new TypeScript. This is a small surface area relative to the value it provides.
